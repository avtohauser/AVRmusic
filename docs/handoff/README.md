# Бриф для агента на ПК пользователя

Ты продолжаешь работу над **AVR ecosystem** — своими сервисами пользователя для него и 2–3 друзей. До тебя всё делала
облачная сессия Claude Code: у неё не было доступа к серверам (нет исходящего SSH, закрыты Google Maven, JitPack и DNS
avthsr.space), поэтому всё, что требует сервера, переходит к тебе. У тебя — ПК пользователя с полной сетью и его
SSH-доступом.

Короткие правила — в [`CLAUDE.md`](../../CLAUDE.md) (загружается сам). Здесь — всё остальное: что есть, как устроено,
что делать и в каком порядке.

---

## 1. Пользователь и как с ним работать

- Пиши **по-русски**, коротко и по делу. Спрашивай, когда решение за ним (что переделать на сайте, где хранить исходники,
  какой вариант выбрать). Вопросы задавай пачкой, с вариантами и своей рекомендацией.
- Пользователь — единственный администратор. Сервисы закрытые, вход по одноразовым приглашениям.
- После сборки APK — ссылка на https://github.com/avtohauser/AVRmusic/releases/latest. IPA — только когда попросит
  (macOS-раннер дорогой).
- Не делай «тихо»: что сделал, что проверил, что не получилось — честно, с выводом команд.

## 2. Безопасность (повтор из CLAUDE.md, это важнее всего)

1. **Репозиторий публичный.** Никаких IP, паролей, токенов, cookies, `.env`, персональных данных, конфигов и
   исходников бэкендов с сервера — ни в коде, ни в коммитах, ни в релизах, ни в логах CI. Даже в зашифрованном виде.
   Перед каждым коммитом смотри `git diff --staged` глазами.
2. **Не проси секреты в чат.** Для SSH — ключ: пусть пользователь сам сделает `ssh-keygen` и `ssh-copy-id`, если ключа
   ещё нет; для CI — GitHub Secrets (он заводит их сам в Settings → Secrets). Ключи сервисов — в админке avr music.
3. Не печатай секреты в терминал: не делай `cat .env`, `printenv`, `docker inspect` без `--format`, `nginx -T` целиком
   в чат. Если нужно узнать, задана ли переменная, — проверяй наличие (`grep -c '^JWT_SECRET=' .env`), а не значение.
4. Команда терминала `coffi` на основном сайте показывает координаты — это личное. Не цитируй, не переноси в документы.
5. Пароль root сервера-хранилища однажды попадал в чат — считай его скомпрометированным и предложи пользователю
   сменить его и перейти на вход по ключу (сам не меняй).

## 5. Как собирать и проверять локально

```bash
pnpm install
cp apps/api/.env.example apps/api/.env      # поправить JWT_SECRET и пути
pnpm seed                                   # демо: admin / admin123, demo / demo123 (только локально!)
pnpm dev                                    # API :8080 + сайт http://localhost:5173

pnpm --filter @avrmusic/api test            # тесты API (node --test)
pnpm --filter @avrmusic/api typecheck
cd apps/web && npx tsc --noEmit -p . && npx vite build

cd android && gradle :app:assembleDebug     # Android (debug, без подписи релиза)
cd android && gradle :shared:compileKotlinIosArm64 -Pkotlin.native.enableKlibsCrossCompilation=true   # iOS-код компилируется

cd tube && gradle :engine:shadowJar && java -jar engine/build/libs/engine.jar   # движок avrtube на :8090
curl 'localhost:8090/search?q=lofi'                                           # с домашнего IP видео тоже должно открываться
```

Для проверки интерфейса удобно гонять Playwright (Chromium) по `localhost:5173` и смотреть скриншоты на ширине
телефона (390px) и компьютера (1440px), в светлой и тёмной теме.

## 6. CI/CD — что надо знать

| Workflow | Когда | Что |
|---|---|---|
| `deploy.yml` | каждый push в рабочую ветку | копирует код на сервер в `/opt/avrmusic`, запускает `deploy/install.sh`, ждёт health, печатает отчёт |
| `android.yml` | push в `android/**` или `package.json`, вручную | подписанный APK (R8), релиз `android-v<версия>`; ключ подписи хранится на сервере |
| `ios.yml` | push в iOS-часть — только проверка компиляции; IPA — **только вручную** | IPA на `macos-15-intel`, heap 10g, таймаут 120 мин, релиз `ios-v<версия>` |
| `tube.yml` | push в `tube/**` | собирает движок и пробует его на YouTube (итоги — в `::notice`) |
| `storage.yml` | вручную: setup / migrate / cleanup / watchdog | обслуживание сервера-хранилища |
| `sites.yml` | вручную | снимок публичных страниц avthsr.space в `sites/mirror/` (kgs, lks54, music пропускает) |

- Версия приложения = `version` из `package.json` + номер сборки (`0.1.0.<run>`). Приложение Android обновляется само.
- Ошибки компиляции Kotlin `.github/scripts/build-errors.sh` превращает в аннотации — их видно в сводке запуска
  (у аннотаций лимит 10, скрипт их ужимает). Логи смотри через `gh run view --log-failed`.
- Красный CI после твоего push — исправляй сразу. Не отключай и не пропускай тесты, не делай пустые коммиты «чтобы
  перезапустить».

## 7. Сервер

Что известно (адреса — в GitHub Secrets и у пользователя, сюда их не пиши):

- Основной VPS: nginx на хосте обслуживает все сайты avthsr.space; сертификаты — certbot.
- avr music: Docker Compose (`docker-compose.prod.yml`) в `/opt/avrmusic`, данные в `/srv/avrmusic`,
  `PROXY=nginx` — приложение слушает `127.0.0.1:$APP_PORT`, nginx проксирует. Ключ подписи APK —
  `/srv/avrmusic/android-keystore/` (его бэкап критичен).
- Сервер-хранилище (второй VPS): музыка лежит там и монтируется на основной по WireGuard; через него же выходят
  скачивания (tinyproxy, `DOWNLOAD_PROXIES`); сторож следит за связью. Скрипты — `deploy/storage/`.
- YouTube режет адреса дата-центров: видео отдаёт `LOGIN_REQUIRED`. Для музыки это решено аккаунтами,
  которые друзья «дарят» через админку (cookies хранятся только на сервере).
- Где лежат исходники основного сайта и его бэкенда — **неизвестно**, это первое, что надо выяснить.

### Как подключаться

- Через SSH-ключ с ПК пользователя. Если ключа нет — попроси пользователя настроить вход по ключу самому; пароль в чат
  не проси. Проверка: `ssh <хост> true`.
- Чтение — согласовано. Изменения — только после того, как показал план и получил «да».

### Безопасное изменение на сервере (сайты, nginx)

1. Бэкап: `tar czf /root/backup/<что>-$(date +%F-%H%M).tgz <папка сайта> /etc/nginx/sites-available/<конфиг>`.
2. Изменение — только в файлах своего сайта. Чужие конфиги (kgs, lks54) не открывать на запись.
3. `nginx -t` → если ок, `systemctl reload nginx` (не restart).
4. Проверка **всех** доменов: `for d in avthsr.space www.avthsr.space explore.avthsr.space old.avthsr.space music.avthsr.space kgs.avthsr.space lks54.avthsr.space; do curl -s -o /dev/null -w "%{http_code} $d\n" https://$d; done`
   — коды должны быть такими же, как до изменения.
5. Откат: распаковать бэкап, `nginx -t`, `reload`.
6. Лучше всего — выкладка сайтов через GitHub Actions (как у avr music), а не руками: тогда каждое изменение — коммит.

## 9. Задачи — по порядку

### 9.1. Обзор сервера (только чтение) — начни с этого

Цель — понять, что где лежит, ничего не меняя. Вывод — **только в чат и в локальные файлы на ПК**, в репозиторий не
коммитить.

- Система: `uname -a; cat /etc/os-release; uptime; free -h; df -h`.
- Сайты nginx: `ls -la /etc/nginx/sites-enabled /etc/nginx/conf.d`; для каждого конфига — `server_name`, `root`,
  `proxy_pass` (grep по ним, а не весь `nginx -T` в чат).
- Процессы и порты: `ss -ltnp`, `systemctl list-units --type=service --state=running`, `pm2 list` (если есть),
  `docker ps -a --format '{{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'`, `docker compose ls`, `crontab -l`, таймеры systemd.
- Где проекты: `/var/www`, `/srv`, `/opt`, `/home/*`, `/root` — по `root` и `proxy_pass` из nginx найди папку каждого сайта.
  Для каждого: размер, есть ли `.git` (`git remote -v`, `git log -5 --oneline`), чем собран (package.json, vite.config).
- Пропускай kgs и lks54 целиком; не открывай `.env`, ключи, базы, логи с личными данными.

Итог для пользователя: таблица «домен → папка → чем отдаётся (статик/прокси на порт/контейнер) → есть ли исходники
и git → как собирается». Отметь странности (например, основной сайт отдаётся как dev-сборка Vite).

### 9.2. Исходники основного сайта под версионный контроль

Сайт `avthsr.space` сейчас — React + Vite, **отдаётся dev-сборкой**, данные — с бэкенда `/api/data` (запасной
`/data.json`), есть вход и правка плиток. **Спроси пользователя**, где хранить исходники:

- (a) в этом публичном репозитории, в `sites/main/` — только фронтенд, без бэкенда и без данных/паролей;
- (b) в отдельном **приватном** репозитории (пользователь создаёт сам) — фронт и бэкенд;
- (c) только на ПК/сервере, без GitHub.

Рекомендация: фронтенд — (a), бэкенд — (b) или (c): его конфиги и данные не должны попасть в публичный репозиторий.
Перед любым коммитом проверь, что нет `.env`, токенов, паролей, личных данных и координат из `coffi`.

### 9.3. Основной сайт в стиле avr

- Переведи сайт на стиль avr (светлая + тёмная тема с переключателем, шрифты, формы, движение) — компоненты из
  `brand/`, бенто-плитки → `.avr-card` с expressive-углами, навигация, лента, страница поста.
- **Сохрани все пасхалки**: каждый маршрут (включая скрытые `/white-space`, `/black-space-2/*`), каждую команду
  терминала, звуки, глитчи, «уровень доверия», счётчики и всё, что сайт помнит в браузере (ключи `localStorage` — те же,
  чтобы у посетителей не сбросился прогресс). Список — `sites/README.md`. Терминал может остаться «терминальным» по
  виду — это часть пасхалки; обсуди с пользователем, насколько его стилизовать.
- Почини: выкладывай **production-сборку** (`vite build`) вместо dev-сервера; проверь мобильную вёрстку (390px),
  консоль без ошибок, Lighthouse.
- Прежде чем верстать, покажи пользователю план и 1–2 скриншота макета; спроси, что ещё он хочет поменять.
- Выкладка — по процедуре из раздела 7 (бэкап, проверка, откат), лучше — через workflow.

### 9.5. avrtube

Готово: `tube/model` (модели), `tube/core` (NewPipeExtractor v0.26.5: поиск, подсказки, тренды, видео с потоками,
канал, плейлист, комментарии; страницы — токен base64url), `tube/engine` (Ktor на :8090, кэш в памяти, подписанный
HMAC прокси потоков `/proxy` с белым списком хостов YouTube, переписыванием HLS и сроком 6 ч). CI: поиск, подсказки,
тренды и комментарии работают; видео на раннерах GitHub — `LOGIN_REQUIRED` (дата-центр).

Дальше:

1. **Сервер.** Сервис `tube` в `docker-compose.prod.yml` (образ из `tube/engine/Dockerfile`; jar собирать в CI или
   многоступенчатым Dockerfile), наружу не публиковать. В Fastify — маршруты `/api/tube/*` → движок:
   всё, кроме `/api/tube/proxy`, под `app.authenticate` (только свои); `/api/tube/proxy` — без входа (ссылки и так
   подписаны, а AVPlayer не умеет слать заголовок авторизации), с поддержкой Range и потоковой передачей.
   Переменные: `TUBE_PROXY_SECRET` (генерировать на сервере в `.env`, как `JWT_SECRET`), `TUBE_PUBLIC_BASE=/api/tube`.
   В nginx для `/api/tube/proxy` — `proxy_buffering off`.
2. **Видео для iPhone с сервера.** Дата-центр YouTube режет. Варианты (обсуди с пользователем): cookies подаренных
   аккаунтов (как у музыки) — передать движку через заголовки запросов NewPipe; запасной путь через `yt-dlp` с теми же
   cookies; выход через сервер-хранилище. Проверь, что реально работает, прежде чем строить.
3. **Приложение** (KMP + Compose Multiplatform, стиль avr, иконка — звезда, слово-знак avr<i>tube</i>): на Android
   движок `tube/core` работает прямо на телефоне (потоки идут напрямую с YouTube на домашний IP), на iPhone — через
   `/api/tube`. Экраны: главная (тренды/подписки), поиск с подсказками, видео (плеер, главы, описание, похожие,
   комментарии), канал, плейлист; фон и «картинка в картинке»; скачивание; подписки и история — локально и/или на
   сервере avr music. Вход — тем же аккаунтом avr music.
4. **Связь с avr music**: «найти этот трек в avr music» / «добавить в библиотеку» для музыкальных видео
   (через каталог и очередь скачивания avr music); общий аккаунт.
5. CI: сборка APK avrtube и проверка iOS-кода по образцу `android.yml`/`ios.yml`, отдельные теги релизов (`tube-android-v…`).

### 9.6. avrgram (Android)

- Основа — **AyuGram для Android** (репозиторий AyuGram4A; форк Telegram, уже умеет режим призрака и сохранение
  удалённых/изменённых сообщений). Лицензия у него, как у Telegram для Android, — GPL (точную версию проверь в его
  `LICENSE`): исходники форка обязаны быть открытыми — в `gram/` положи ту же лицензию, остальной репозиторий остаётся MIT.
- Исходники Telegram огромные — не копируй их в репозиторий целиком. Предложи пользователю: `gram/` хранит только наши
  патчи + скрипт, который берёт AyuGram на зафиксированном коммите и применяет патчи; CI собирает APK.
- `TELEGRAM_API_ID` / `TELEGRAM_API_HASH` — пользователь получает на my.telegram.org и кладёт в GitHub Secrets сам.
- Функции защиты (первая волна): режим призрака, сохранение удалённых и изменённых, локальная база под паролем
  (шифрование), «паник-кнопка» (быстрое стирание), удаление метаданных из отправляемых фото/файлов, проверка ссылок
  и файлов, аудит активных сеансов, прокси. Потом пользователь добавит ещё.
- Стиль: тема avr (светлая/тёмная), шрифты, иконка-звезда, слово-знак avr<i>gram</i>.

### 9.7. Сопровождение avr music

Друзья присылают баги — чини, прогоняй проверки, выпускай APK (push в `android/**`), давай ссылку на релиз.

## 10. Чего не делать

- Не трогать kgs, lks54 и old. Не ломать чужие сайты на nginx.
- Не публиковать ничего с сервера в публичный репозиторий и релизы (конфиги, исходники бэкендов, дампы, логи).
- Не просить и не печатать пароли, токены, cookies.
- Не делать изменений на серверах без явного «да» пользователя.
- Не править avr music руками на сервере — только через git и деплой.
- Не обходить сетевые ограничения и защиту сервисов.
